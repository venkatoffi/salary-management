# Salary Management System

A simple web application for managing **employees, departments, and salaries** for an organization of approximately 10,000 employees.

Built as an engineering assessment with a focus on **clarity, maintainability, performance, testing, and practical design decisions**.

## Tech Stack

- **Frontend:** React.js
- **Backend:** Ruby on Rails REST API
- **Database:** PostgreSQL
- **Testing:** Rails test + frontend tests
- **Deployment:** Docker

## Main Features

### HR Manager / Chief

- View and search employees
- Filter employees by department, country, city, and salary range
- Add employees
- View employee details
- Manage departments
- View department heads and employee counts
- View current salaries
- View salary revision history
- View payslips

### Department Head

- View their department
- View employees in their department
- View relevant salary information

### Employee

- View their profile
- View current salary
- View salary history
- View payslips

## Core Database

```text
roles
  │
  ▼
users
  ├── authentications
  ├── salaries
  ├── salary_revisions
  ├── payslips

```

The `users` table represents both **employees and application users**.

## Getting Started

### 1. Clone the repository

```bash
git clone <repository-url>
cd salary-management
```

### 2. Start the application

```bash
docker compose up --build
```

The frontend and backend services will start using Docker.

### 3. Database

The application should create/setup the PostgreSQL database through the Rails setup process.

Typical Rails commands:

```bash
rails db:create
rails db:migrate
rails db:seed
```

The seed process creates approximately **10,000 employees** for testing search, filtering, pagination, and salary functionality.

## API

The backend exposes a versioned REST API:

```text
/api/v1/
```

Main resources:

```text
POST   /api/v1/salaries
GET    /api/v1/salaries
GET    /api/v1/salaries/:id
PATCH  /api/v1/salaries/:id
GET    /api/v1/users/:user_id/salary_revisions
POST   /api/v1/users/:user_id/salary_revisions
GET    /api/v1/payslips
GET    /api/v1/payslips/:id
GET    /api/v1/users
```

Salary endpoints support `POST`, `GET` collection, `GET` by ID, and `PATCH` by
ID. Salary revisions support `POST` and `GET` at
`/api/v1/users/:user_id/salary_revisions`. Updating a salary and recording its
revision are committed in one database transaction. Salary revisions belong
directly to users; salaries remain one current record per user. Payslips are
stored per user/month/year with unique period and non-negative amount
constraints and are available through read-only list and detail endpoints.
Employee listing supports server-side `search`, `department_id`,
`country_code`, `city`, `employment_status`, `min_salary`, and `max_salary`
filters, plus bounded `page` and `per_page` pagination. Payslip listing accepts
`user_id`, `month`, `year`, `page`, and `per_page`.
Successful salary/revision creates return `201`, reads and salary updates
return `200`, and invalid data returns `422` with an `errors` array.

Authentication endpoints are available directly at `/login`, `/logout`, and
`/current_user`. The version-prefixed authentication routes remain available
as compatibility aliases.

Authentication uses Devise to verify passwords and Rails to sign and verify
JWTs. Set `JWT_SECRET_KEY` to a secret generated by
`cd backend && bin/rails secret` in your environment/secret manager, or store it
as `jwt_secret_key` in Rails credentials. For local development, run
`export JWT_SECRET_KEY="$(bin/rails secret)"` from `backend/`. The server
requires one of these settings and rejects signing keys shorter than 32 bytes.
Never send the signing secret to the frontend.

Log in with `POST /login` and JSON
`{ "user": { "email": "...", "password": "..." } }`. The response body contains
`auth_token`, `expires_at`, and minimal user/permission details. Send the raw
JWT as the complete value of the `Authorization` header:
`Authorization: <auth_token>`.
Use `GET /current_user` to restore the signed-in user's details, and
`DELETE /logout` to revoke that token. JWT payloads contain only user,
role, department, session IDs, and issue/expiry timestamps; the server also
checks that the persisted authentication session remains active and unexpired.

The root `GET /` and login `POST /login` are public. There is currently no
`POST /signup` route; user creation remains restricted to authorized admins.
All other API endpoints require a valid raw-token `Authorization` header.

In the React client, treat the token as opaque: do not decode it or make
authorization decisions from its contents. Store it using the application's
session storage, set `Authorization` directly to the token value on every
protected API request, and use the current-user endpoint for UI state.
Backend authorization remains authoritative. Chiefs and HR Managers can
access all records and manage them. Department Heads can read records in their
department. Employees can read only their own profile, salary, salary
revisions, and payslips; department access is forbidden.
Unauthorized requests return `403`; requests without a valid token return
`401`. Collection endpoints are scoped before querying and paginated. Passwords
are stored as Devise `encrypted_password` hashes and are never included in API
responses.

Development seeds assign the shared password `SalaryDemo2026!` to users whose
password is not already set. This is a demo credential: change it immediately
and do not use it outside local development. Production seeding requires the
`INITIAL_USER_PASSWORD` environment variable.

## Performance

The application uses:

- Server-side pagination
- Server-side filtering
- Database indexes
- Efficient ActiveRecord queries
- N+1 query prevention
- Small API responses
- Search debouncing

The expected scale of 10,000 employees does not require microservices or a distributed architecture.

## Testing


Frontend tests:

## Design Principle

> **Keep it simple, make it correct, and optimize where it matters.**

The project intentionally avoids unnecessary complexity such as microservices, Kafka, Kubernetes, Elasticsearch, payroll processing, tax calculation, and payment processing.

The goal is a clean, understandable, production-minded application that solves the salary-management problem well.
